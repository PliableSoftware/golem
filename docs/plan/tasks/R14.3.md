## What this is

USER decision (2026-09-19, superseding this task's earlier scope): Golem
should appear in Buzz as its **own peer harness** — on par with `goose`,
`claude`, `codex` in Buzz's harness picker — not as a Claude Code session
running underneath the existing `claude` harness. Concretely: Buzz's per-agent
"Loadout" harness field gets a `golem` option, and choosing it means Buzz
spawns *Golem's* runtime (redaction, compression, routing, local tools,
telemetry — the full pipeline this repo builds) rather than a bare Claude
Code process that Golem happens to be proxying in front of.

This is the foundational task for the whole Buzz effort. R14.2 (persona/
orchestrator identity provisioning) and R14.4 (orchestrator dispatch
behavior) both assume harness `golem` already exists and can complete a turn
— do not start those until this one's gate is met in isolation, with nothing
persona- or orchestration-specific layered on yet.

Read [[Buzz Integration]] first. This task implements the "Golem as harness"
decision recorded there; it does not itself decide persona mapping or
dispatch behavior (that's R14.2/R14.4).

## Must

- Confirm the actual ACP surface (message shapes, session lifecycle, how a
  harness registers with / is spawned by Buzz) against `block/buzz` source or
  a real ACP spec — this is explicitly unverified today (verification-notes.md
  §17). Do not guess the protocol shape from the engineering blog's UI-level
  description alone.
- Golem process implements that surface as harness `golem`: it can be spawned
  by Buzz, receive a turn, run its own pipeline end to end, and reply in a
  form Buzz understands as a normal harness turn.
- Model selection continues to flow from the Buzz agent config's `model`
  field into Golem's existing routing (same principle as `inference.personas`
  already uses) — Golem does not hardcode a model when acting as the `golem`
  harness.
- Ship the minimal case first: one Buzz agent, harness `golem`, no persona or
  orchestrator wiring, that can hold a plain conversation turn. That is the
  gate. Persona/orchestrator behavior is out of scope here.

## Must not

- Do not implement persona-specific or orchestrator-specific behavior in this
  task — that couples the protocol layer to behavior that belongs in
  R14.2/R14.4 and makes both harder to verify independently.
- Do not fall back to silently reusing the `claude` harness under a `golem`
  label if the real ACP surface turns out to be more involved than expected.
  If it's a large lift, say so and let R14.2/R14.4 stay blocked rather than
  shipping a harness that only partially speaks the protocol.

## Verification bar

Standing suite per `CLAUDE.md`. Because this depends on an external, only
partially documented protocol, expect a `verification-notes.md` entry before
any implementation — record what was confirmed against the real ACP spec /
`block/buzz` source, dated, before writing the harness code itself.
