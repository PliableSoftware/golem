## What this is

USER decision (2026-09-19): Golem appears in Buzz as its **own peer runtime** —
`golem`, alongside `goose`, `claude`, `codex` — not as a Claude Code session
riding the existing `claude` harness with Golem's proxy in front of it.

Research since then (`verification-notes.md` §19) established that this is a
**much smaller lift than the brief originally assumed, and points the opposite
way round**. Read §19 before anything else. The short version:

- **ACP is a real public protocol** — Agent Client Protocol, by Zed Industries,
  JSON-RPC 2.0 over stdin/stdout, spec at `agentclientprotocol.com`.
- **Buzz is the ACP *Client*; Golem is the ACP *Agent*.** `buzz-acp` (a Rust
  crate in `block/buzz`) holds the relay WebSocket and spawns an agent
  subprocess over stdio. What Buzz's UI calls a "harness" is just that
  subprocess command. Nothing is registered *inside* Buzz, and nothing needs to
  be contributed to `block/buzz`.
- So "Golem as its own harness" = **ship a `golem acp` subcommand** that speaks
  ACP on stdio, and point `BUZZ_ACP_AGENT_COMMAND` at it.

```
Buzz Relay ──WS──→ buzz-acp ──stdio(ACP/JSON-RPC)──→ golem acp
                                                         │
                                                    buzz-cli
                                                 (messages send, …)
```

This is the foundational task. R14.2 (identity provisioning) and R14.4
(orchestrator dispatch) both assume `golem acp` completes a turn. Ship the
plain-conversation case only.

## The protocol surface, exactly

`buzz-acp`'s own README (§ "Using Any ACP Agent") states the whole requirement.
Four things:

1. Accept `initialize` and return a result.
2. Accept `session/new` with `mcpServers` and return a `sessionId`.
3. Accept `session/prompt` with a text message and stream `session/update`
   notifications.
4. Return a `stopReason`.

The `stopReason` enum is **exactly five values** and has no error member
(`verification-notes.md` §20 item 2, read off the spec): `end_turn`,
`max_tokens`, `max_turn_requests`, `refusal`, `cancelled`. §19's trailing "etc."
was wrong. Two of them are not free — `buzz-acp` **rotates (discards) the ACP
session** on `max_tokens` and `max_turn_requests`
(`crates/buzz-acp/src/pool.rs:3240-3243`), and no `stopReason` of any kind is
ever posted to the channel; every one of them produces a `tracing::warn!` and
nothing else (`pool.rs:4830-4842`). **Nothing you put in a `stopReason` reaches
a human.** That fact drives the rate-limit policy below.

Everything else in ACP — `session/load`, `session/set_mode`, `fs/*`,
`terminal/*`, `elicitation/*`, `session/request_permission` — is optional and
capability-gated. Do not implement any of it in this task.

## Lane transparency: a worker-lane persona is a Buzz agent too

USER requirement (2026-09-19), added after the brief was first written: a
worker-lane persona must be **just as addressable in Buzz** as an agent-lane
one. Same `@mention` handle, same identity, same prompt source, same model
source — only the execution mechanism differs, and it differs *behind* the
identity. A live model change (as `coder` had on 2026-09-19, moving it to a free
OpenRouter target) must not add or remove a Buzz identity; it may only change
what happens inside that identity's next turn.

Read [[Buzz Integration]]'s "Lane-transparent dispatch" section and
`verification-notes.md` §21 before building this. The short version:

- **Addressability is lane-agnostic and is R14.2's job**, not this task's. Do
  not special-case a worker-lane persona anywhere in `golem acp`.
- **Framing is lane-agnostic and IS this task's job.** Prompt from
  `resolvePersonaPrompt()`, model from `inference.personas.<id>.model`,
  whichever lane runs.
- **Execution capability is not equalisable**, because it is a property of the
  model. A persona staffed on a 4B local target cannot drive a tool loop
  wherever it runs. R14.3 ships the honest version of that, not a pretence.

### Scope: this task ships a one-shot for BOTH lanes

R14.3's scope is already *"the plain-conversation case only"*, and for
conversation a bounded single-shot is the **correct** execution mode rather than
a degraded one — someone asking `@golem-reviewer` for an opinion wants an
answer, not a file edit. So:

> `acp-turn.ts` resolves the lane, and **both branches run a bounded
> single-shot** through `target-dispatcher.ts` with the persona's prompt and the
> persona's model. The worker lane dispatches to its registry target; the agent
> lane dispatches its model id against the resolved default target.

Borrowing a real agent loop for agent-lane turns — by nesting
`@agentclientprotocol/claude-agent-acp` as a child ACP Agent — is **confirmed
viable** (§21) but is explicitly **not this task**. It carries a heavyweight
native optional dependency and an unsettled permission decision, and folding it
into an already size-M brief makes neither half reviewable. See "Must not".

**So write the executor behind one interface** — something like
`runPersonaTurn(ctx): AsyncIterable<Chunk>` chosen by lane — so adding the
nested executor later changes one module and nothing else. That is the whole
architectural ask here.

### Two defects to fix, because the brief's assumptions are currently false

Both found 2026-09-20 (§21 item 13). Neither is optional.

1. **`resolvePersonaPrompt()` is lane-agnostic as a function, but no worker-lane
   dispatcher calls it.** `src/mcp/coder-tools.ts:133` hardcodes
   `resolveCoderPrompt(grounding.coderPrompt)` and never reads
   `.golem/personas/coder.md`; `src/cli/persona-sync.ts:98-104` calls
   `resolvePersonaPrompt()` for every persona **but** special-cases `coder` to
   `resolveCoderPrompt()` when neither `prompt` nor `prompt_file` is set. The
   lanes disagree about the coder's prompt today.

   **`golem acp` must call `resolvePersonaPrompt()` for every persona in every
   lane** — and that means deciding the `inference.coder_prompt` collision
   explicitly rather than inheriting it. Recommended: mirror `persona-sync.ts`
   exactly (so `coder` in Buzz reads the same prompt as `golem-coder` in Claude
   Code), and say in the PR that the `coder` MCP tool remains the odd one out.
   Taking the other path — `resolvePersonaPrompt()` unconditionally — is
   defensible, but then `inference.coder_prompt` silently stops applying to one
   of its two documented consumers, so it must be called out either way.
2. **`DispatchRequest` has no model override.**
   `src/inference/target-dispatcher.ts:153-183` accepts `targetId` or `worker`
   and otherwise falls through to `inference.model`, then the synthetic
   `"harness"` default over `proxy.upstream_*`. An agent-lane model id names no
   registry target **by definition** — that is what makes it agent-lane — so
   Golem cannot dispatch it at all today, even as a one-shot. Add an optional
   `model?: string` to `DispatchRequest`, honoured over the target's own default
   model. Same file as `RateLimitedError`, so it is one visit.

### Resolve the lane per TURN, cached for that turn

The persona is bound at spawn (`--persona <id>` arrives via
`BUZZ_ACP_AGENT_ARGS`, and `buzz-acp` respawns with the same environment), so
identity cannot drift. The **lane** can: it derives from
`inference.personas.<id>.model`, which a settings edit changes live.

- **Read settings at turn start, once, and cache for the turn.** A settings edit
  must never make one turn change execution style halfway through.
- **Do not add a file watcher.** `src/cli/persona-watcher.ts` exists to
  regenerate *artifacts*; a headless daemon that consumes the value at turn
  start gains only a race by watching. (`verification-notes.md` §166 records the
  analogous staleness bug on the Claude Code side — reading at turn start is the
  version of that which does not have it.)
- **Record the resolved lane in the thread state R14.4 reads.** A thread
  deferred under one lane and resumed after a settings change would otherwise
  switch execution style silently mid-sequence.
- `resolvePersonaLane()` **throws** `PersonaLaneError` for a model naming
  neither a target nor a plausible model id. In a headless turn that must become
  one honest channel message and `stopReason: end_turn` — never an unhandled
  rejection that takes the process down and triggers a `buzz-acp` respawn loop.

### How this interacts with the rate-limit policy below

For both branches this task ships, **the MUST HANDLE policy is unchanged** —
worker lane and agent-lane one-shot both go through `target-dispatcher.ts`, so
one `RateLimitedError` path covers both. Nothing below needs a lane branch.

That stops being true for a nested agent loop, which is one more reason it is a
separate task: Golem would never see the 429 (it happens inside the child), and
the bounded in-turn retry would be actively wrong, because a nested turn may
already have written files and is therefore not idempotent to replay. §21 and
[[Buzz Integration]] record the four differences. Do not pre-build for them.

## Implementation plan

### Dependency — settled (USER, 2026-09-19): `@agentclientprotocol/sdk`

Standards approach, not hand-rolled: depend on `@agentclientprotocol/sdk`
(npm, official TypeScript library) rather than reimplementing JSON-RPC-over-
stdio by hand. Use the fluent `agent()` entry point; `AgentSideConnection` is
deprecated.

Checked before settling (2026-09-19): `1.4.0`, **zero declared runtime
dependencies**, `5,586,531` bytes unpacked (~5.6 MB). Pure TypeScript over
JSON-RPC with no native bindings, so it satisfies `CLAUDE.md`'s "no
heavyweight native deps in default install" and becomes a normal runtime
dependency of the default install (`golem acp` is a CLI subcommand, so it
ships in the default tarball, not an optional add-on). Pin it in
`package.json` the way other direct deps are pinned in this repo.

**Use ACP v1 — the stable package entry point. Do not import
`@agentclientprotocol/sdk/experimental/v2`** (§21 item 2). v2 ships inside the
same package and carries its own warning: *"ACP v2 is still a draft. Its wire
protocol and this TypeScript API may change incompatibly in any SDK release."*
This brief's earlier note that "a v2 draft already exists" was an argument for
depending on the SDK at all, not a suggestion to use v2.

**The same package also ships the CLIENT side** — `client({ name })` with
`requestPermission(...)` / `sessionUpdate(...)` handlers, plus
`connectWith(stream, async (ctx) => …)` (§21 item 2). R14.3 does not need it,
but it is why the nested agent-lane path (below) costs no new dependency.

The rejected alternative — hand-rolling the ~300-line JSON-RPC surface for
zero added dependencies — trades a small footprint for tracking ACP's schema
by hand as the spec evolves (a v2 draft already exists); the SDK amortizes
that tracking across everyone using it instead of this repo alone.

### Files, in the order to touch them

1. **`src/buzz/types.ts`** — Zod schemas for the four inbound message shapes.
   `buzz-acp` is an external boundary, so validate at it per `CLAUDE.md`;
   trust the types inward from there. Keep these local to `src/buzz/` — **do
   not add anything to `src/interfaces/`**, which is frozen.
2. **`src/buzz/acp-session.ts`** — the session registry: `sessionId` →
   `{ cwd, mcpServers, personaId, history }`. `session/new` mints one; a
   session outlives a turn, and `buzz-acp` may `!rotate` it away underneath us.
3. **`src/buzz/acp-turn.ts`** — runs one turn: takes the prompt text, feeds it
   through Golem's existing pipeline and routing (redaction, compression,
   provider selection), emits `agent_message_chunk` `session/update`
   notifications as output arrives, and resolves to a `stopReason`. Model
   selection reads `inference.personas.<id>.model` via `personaModel()` in
   `src/inference/personas.ts` — **never hardcode a model here**. The prompt
   comes from `resolvePersonaPrompt()` in the same module, for every persona in
   every lane (see "Two defects" above).

   **This is where the lane branch lives.** Call `resolvePersonaLane()` from
   `src/inference/persona-lane.ts` once per turn, then dispatch through the
   single executor interface: worker lane → its registry `targetId`; agent lane
   → the resolved default target with the persona's model as the new
   `DispatchRequest.model` override. One branch, at the top; everything after it
   is shared. Keep it small enough that a third branch (the nested executor)
   slots in without restructuring.
3b. **`src/inference/target-dispatcher.ts`** — two additions, one visit:
   the optional `model?: string` on `DispatchRequest` (above) and
   `RateLimitedError` (below). Both are small, both benefit every other Golem
   caller, and neither belongs in `src/buzz/`.
4. **`src/buzz/limit-guard.ts`** — the rate-limit / usage-cap policy for a turn
   (see "MUST HANDLE" below): the pre-flight check, the bounded in-turn retry
   budget, and the decision to defer. Keep it a **pure decision module** taking
   a `LimitPrediction` and a classified dispatch error and returning
   `proceed | retry(afterMs) | defer(untilIso, reason)`, so it is testable with
   a faked clock and no network. It reuses `decideSnoozeNudge()` rather than
   restating the threshold.
5. **`src/buzz/acp-agent.ts`** — wires 1–4 to the SDK's `agent()` over
   `process.stdin` / `process.stdout`. **Nothing may write to stdout except the
   JSON-RPC stream** — logging goes to stderr or a file, or the protocol
   corrupts. This is the single most likely way to break this task.
6. **`src/cli/commands/buzz.ts`** — the `golem acp` subcommand (plus a
   `--persona <id>` flag R14.2 will use), registered from
   `src/cli/program.ts` alongside the other command modules.
7. **`src/buzz/harness-definition.ts`** — emits the Buzz Desktop "Bring Your
   Own Harness" tier-3 JSON (`{"id":"golem","label":"Golem","command":"golem",
   "args":["acp"], …}`) for `<app-data>/custom_harnesses/golem.json`. `golem`
   is confirmed available — the reserved namespace is tier-1 (`goose`,
   `claude`, `codex`, `buzz-agent`) plus the tier-2 presets. **Emit the file
   only; installing it into Buzz's app-data directory is R14.2's job.**
8. **`tests/unit/buzz/`** — a scripted fake ACP client driving the four
   methods, plus recorded-shape tests for the JSON-RPC envelopes. `block/buzz`
   tests its own side this way (PR #7359 adds "a scripted fake agent"); the
   mirror image is how Stage 1 is verified without a relay. Add the rate-limit
   cases: a 429 inside the retry budget retries and completes; a 429 outside it
   defers, posts exactly one channel message, and returns `end_turn`; a `park`
   pre-flight verdict never dispatches at all; a `stale` reading never blocks.

### Non-obvious constraints, all confirmed

- **`BUZZ_ACP_IDLE_TIMEOUT` defaults to 620 seconds and resets on any agent
  stdout activity.** A turn that thinks quietly for over ten minutes is
  cancelled. Streaming `session/update` is therefore the keepalive as well as
  the UX — a batch-then-emit implementation will be killed on long turns.
  `BUZZ_ACP_MAX_TURN_DURATION` (7200s) is the hard cap.
- **`BUZZ_ACP_AGENT_ARGS` splits on commas**, so the persona flag arrives as
  `acp,--persona,coder`. Args carrying values use `-c,key="value"`.
- **`buzz-acp` injects `BUZZ_RELAY_URL`, `BUZZ_PRIVATE_KEY` and
  `BUZZ_AUTH_TAG`** into the subprocess environment. `BUZZ_PRIVATE_KEY` is a
  Nostr secret key — it must be in Golem's redaction set before any turn runs,
  and must never reach a log, a telemetry record, or the KB.
- **`session/new` carries `mcpServers`**, the Buzz-managed MCP server among
  them. Accept and store it; this task does not have to call those servers, but
  it must not reject the parameter.
- Cross-platform per `CLAUDE.md`: `node:path`, argument-array spawn, no shell
  string interpolation.

## MUST HANDLE: a rate limit or usage cap mid-turn

**This is a requirement, not a nice-to-have, and nothing in R14.2/R14.3/R14.4
covered it before 2026-09-19.** Golem's existing protection — [[Usage Limit
Park]] and [[Spawn Headroom Gate]] — is a Claude Code `PreToolUse` hook that
denies the next *tool call* and redirects an *interactive session* to call
`snooze`. `golem acp` is a headless daemon reacting to an `@mention` with nobody
watching: no tool-call loop for that gate to sit in front of, and no human to
answer a park prompt. Full evidence in `verification-notes.md` §20 items 1-3.

### Detection — two layers, because one is not enough

The state Golem already keeps is **not** produced by this process.
`.golem/state/limit-state.json` is written from exactly one place,
`src/cli/proxy-build/telemetry-hooks.ts:181-191`, **inside the proxy process**,
as a side effect of proxied traffic. Every reader today is a Claude Code
surface. And `src/inference/target-dispatcher.ts` has **no** rate-limit
awareness at all: `dispatchAnthropic` (:581-585) and `dispatchOpenAI` (:522-526)
collapse every non-ok status into one generic `TargetDispatchError` and throw
`res.headers` away. A 429 is currently indistinguishable from a 500.

So build both halves:

1. **Pre-flight, cheap, advisory.** Before starting the model call, read
   `readLimitState(projectDir)` and run the *existing pure function*
   `decideSnoozeNudge(prediction, state, nowMs)` from
   `src/hooks/snooze-nudge.ts`. It already returns `{kind:"none"|"park"|"stale"}`
   from a `LimitPrediction` — the hook was only ever its delivery channel, so
   reuse the decision and give it a new channel. A `park` verdict means decline
   the turn *before* spending it. Honour `stale` exactly as the hook does:
   a reading older than `STALE_AFTER_MS` (30 min) warns and never blocks,
   because this process may legitimately be the only thing running and the proxy
   may have written nothing for hours.
2. **In-flight, authoritative.** Classify at the dispatch boundary. Add a
   `RateLimitedError extends TargetDispatchError` carrying `status`,
   `retryAfterSeconds` (from the `retry-after` header) and a `LimitPrediction`
   parsed from the *same* response headers with the existing
   `parseLimitPrediction()`. This is the only signal that is synchronous with
   the failing call, and it is a small, self-contained change to
   `target-dispatcher.ts` that every other Golem caller benefits from.

**Strongly preferred wiring, and flag it in the PR either way:** have `golem
acp` dial the project's own proxy rather than the provider directly.
`src/cli/proxy-daemon.ts` binds `127.0.0.1` on a deterministic per-project port
(`PROXY_PORT_BASE = 4653`, span `1000`, derived from the project path,
overridable via `proxy.port`), so this is a base-URL choice, not new
machinery — and it makes limit prediction, redaction, compression and telemetry
apply to Buzz turns exactly as they apply to Claude Code turns, with no second
implementation to keep in sync. The trade-off is a hard dependency on the proxy
daemon being up, which for a headless agent is a supervision question: decide
whether `golem acp` starts it, requires it, or falls back to direct dispatch
with layer 2 only, and **say which in the PR**.

### Policy — end the turn and say so in the channel

Recommended, and it is the same answer the rest of the ecosystem reached:

> On a rate limit or usage cap, **post an honest status message to the channel
> with `buzz messages send`, record the thread as deferred, and return
> `stopReason: end_turn`.** Do not wait, do not hold the turn open.

Why, against the alternatives that were actually considered:

- **Retry-with-backoff inside the turn is structurally impossible for the case
  that matters**, not merely unwise. Anthropic's session window is 5 hours;
  `BUZZ_ACP_MAX_TURN_DURATION` is 7200s (2h). A turn *cannot* outlive the wait.
  Worse, `buzz-acp` holds at most one prompt in flight per channel, so a turn
  sitting on a backoff deadlocks the very channel the resume — and the owner's
  `!cancel` — has to arrive through. Keepalive `session/update`s would defeat
  the 620s idle timeout and make it *more* harmful, not less.
- **A short bounded retry is still right for a short wait.** If `retry-after`
  (or the observed reset) is within a small budget — start at **≤ 60s**, well
  inside the 620s idle timeout — retry in-turn with backoff while streaming
  `session/update` as keepalive. Above that budget, defer. One threshold, one
  place, named as a constant. This is the goose-shaped behaviour (`block/goose`
  defaults to 3 tries / 1s / ×2, §20 item 3) and it handles ordinary
  per-minute throttling without turning every blip into a channel message.
- **The channel message is the only thing that reaches a human.** Confirmed in
  `buzz-acp`'s own source: no `stopReason` is ever posted, and `acp.rs` handles
  `_meta` only for `goose.activeRunId`, `steering.supported`, `systemPrompt` and
  `sessionTitle` — so the `_meta.jetbrains.air.sessionFailure` extension that
  `@agentclientprotocol/claude-agent-acp` uses for exactly this condition would
  be **silently dropped** by Buzz. Emitting it too is cheap forward-compat;
  relying on it is not allowed.
- **`end_turn` is the right stopReason, and the other four are wrong.**
  `max_tokens`/`max_turn_requests` make `buzz-acp` discard the ACP session for
  no benefit and misname the cause; `refusal` reports a transient external
  condition as a policy refusal; `cancelled` is reserved for `session/cancel`.
  `claude-agent-acp` returns `end_turn` for this same condition, verbatim: *"A
  turn-terminal failure is attached to the successful ACP `PromptResponse` in
  `_meta`; the response uses `stopReason: end_turn`."*

The message must be honest and actionable — what happened, when the window
resets, and that it will be picked back up. Something of the shape *"Rate
limited on `<target>`. The session window resets at `<HH:MM local>`; I have
saved where I got to and will pick this up on the next mention after that."*
**Never** imply a guaranteed automatic resume unless the heartbeat is actually
configured (R14.4 settles that).

### Reusing `snooze` — partly, and the part not to reuse

- **Reuse `decideSnoozeNudge()`** (the threshold/staleness policy) so Buzz turns
  and Claude Code sessions park on the same rule rather than drifting apart.
- **Reuse `persistSnoozeNote(projectDir, note, {nowIso})`** from
  `src/mcp/snooze-note.ts` as an **operator breadcrumb** — it files a queued
  local task with no MCP dependency and is fail-open. It makes a deferred Buzz
  thread visible to `golem task list`, which is otherwise the one place a human
  would look and find nothing.
- **Do not reuse `runSnooze()`.** It blocks the live session until the reset;
  here that is the channel deadlock above.
- **Do not attempt to call the `snooze` MCP tool.** There is no tool-call loop
  in an ACP turn and nothing would be listening. `snooze` as built assumes an
  interactive `mcp__golem__snooze` call that does not exist in this process.
- **The resumable state does not belong in a snooze note.** A note is not keyed
  by thread and cannot resume a turn. That state is R14.4's `thread-state.ts`;
  this task must write enough of it to be resumable and must not invent a second
  store.

### Scope split with R14.4

R14.3 owns **detection, the in-turn retry budget, the channel message, and the
`stopReason`** — the plain-persona case, testable with a scripted client and a
faked clock. R14.4 owns **deferral and resumption** (`deferred_until`, the wake
path, the heartbeat decision). Build R14.3's half so a deferred turn writes the
state R14.4 reads; do not build the resume logic here.

## Must not

- Do not implement persona-specific or orchestrator-specific behaviour — that
  is R14.2/R14.4, and coupling it here makes both unverifiable alone.
- **Do not build the nested-ACP executor here.** Spawning
  `@agentclientprotocol/claude-agent-acp` as a child ACP Agent is confirmed
  viable (§21) and is the right eventual answer for agent-lane *work*, but it
  brings a heavyweight native optional dependency, an unanswered permission
  decision, and a rate-limit path that differs from this task's in four ways.
  It gets its own task doc. Leave the seam, not the implementation.
- **Do not make a worker-lane persona behave like a lesser citizen.** It gets
  the same identity, the same prompt source, the same model source and the same
  turn shape. If its answer is more limited, that is the model's doing and
  should read as such, not as Golem declining to serve it.
- Do not read `.claude/agents/golem-<id>.md` as the persona prompt. That file
  exists only for agent-lane personas, so depending on it reintroduces exactly
  the asymmetry this task removes. `resolvePersonaPrompt()` is the source.
- Do not silently reuse the `claude` harness under a `golem` label.
