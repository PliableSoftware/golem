## What this is

DUST4.1 registers the skill; registration alone makes `installSkills` write it. This task proves the lifecycle holds for it and commits this repository's own generated copy. It should need no production code. If a test shows a real defect, fix it at the narrowest point and say so.

## Default: seeded by default (decided here, overturnable)

`/golem-dust` installs on every `golem init`, like every other skill. Reasons:

- **The comparable feature is a skill, not a rule.** All 23 shipped skills install unconditionally from `P0_SKILLS`, including the other long, user-invoked method skills (`first-pancake`, `adversarial-review`, `fresh-eyes`, `checkpoint`). There is no opt-in path for skills today.
- **Opt-in exists for guidance RULES because a rule is always in context and changes behaviour unasked.** `prompt-translation` and `durable-tasks` are `seededByDefault: false` in `src/hooks/guidance.ts` for that reason. A user-invoked skill (`invocationMode: user`) costs only its description line in the skill listing and does nothing until typed.
- Making it opt-in would mean building the first per-skill toggle and seed sentinel, which is a mechanism change for one skill.

## Known wrinkle (pre-existing, all skills)

Deleting a skill directory does not stick: `installSkills` classifies a missing file as `absent` and recreates it on the next init. Guidance rules solved the same problem with the `.golem/state/guidance.json` "offered" record; skills have no equivalent. Write a follow-up task doc `skill-opt-out-sticks` describing that gap (all skills, not just dust) if you confirm it with a test. Do not build it here.
