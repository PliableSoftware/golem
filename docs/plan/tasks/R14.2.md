## What this is

Extend Golem's persona-sync — the mechanism in `src/cli/persona-sync.ts` that
already generates `.claude/agents/golem-<id>.md` per staffed persona — to also
provision a **Buzz identity and launch spec** for each staffed persona plus
Golem's own orchestrator, so `golem-coder`, `golem-planner`, `golem-reviewer`,
`golem-scribe` become independently `@mention`-able in that project's Buzz
workspace.

Read `verification-notes.md` §19 first, then [[Buzz Integration]]. §19 changes
what this task has to build, in two ways that make it smaller:

- **A "Buzz agent" is a `buzz-acp` process holding a Nostr keypair.** There is
  no agent record to POST anywhere. Provisioning an identity means minting a
  keypair, getting its pubkey registered as a relay member, and having a
  process run with that key in `BUZZ_PRIVATE_KEY`.
- **Golem does not have to tell Buzz the model, provider or effort.** Those
  fields only steer tier-1 runtimes whose launch flags Buzz knows. For a
  tier-3 custom runtime Buzz spawns `command` + `args` + `env` and nothing
  else — inference is entirely Golem's business, read from
  `inference.personas.<id>.model` at turn time (R14.3). The mapping table in
  [[Buzz Integration]] has been corrected accordingly.

## Confirmed lane-agnostic (USER requirement, 2026-09-19)

A worker-lane persona must be **just as addressable in Buzz** as an agent-lane
one. This task already satisfies that and must keep satisfying it:

- **Provision by STAFFING, never by lane.** Read `effectivePersonas()` and mint
  one identity per staffed, dispatchable persona. Do **not** mirror
  `resolveDesiredAgents()` in `src/cli/persona-sync.ts`, which filters to
  `lane.kind !== "agent"` at line 92 — that filter is correct there (a
  worker-lane persona has no harness subagent) and would be a bug here. Mirror
  its *staffing* logic only, and say so in a comment, because the two functions
  looking similar is exactly how the filter gets copied across by accident.
- **The launch spec is identical either way**: `BUZZ_ACP_AGENT_ARGS=acp,--persona,<id>`.
  `golem acp` resolves the lane itself, at turn time (R14.3). Nothing
  lane-shaped reaches Buzz.
- **`owner: user` is still the one exclusion**, on the permission axis rather
  than the lane axis. `resolvePersonaLane()` already folds it in
  (`unstaffed / owner-user`), as does `personaModel()`.

### Do NOT record the lane in the manifest

`.golem/buzz/agents.json` is **committed**. A persona's lane derives from
`inference.personas.<id>.model`, which changes live — `coder` moved from a model
id to a free OpenRouter target on 2026-09-19. If the manifest carried the lane,
that edit would produce a committed diff and a PR review for something the Buzz
human is explicitly not supposed to notice. **The manifest is lane-free**:
persona id, pubkey, relay URL, respond-to mode, channel.

Where the lane *should* surface is `golem buzz status`, as derived state read
fresh — "`coder` → worker lane → `openrouter-free:…`" — alongside the roster.
That gives an operator the answer without making a live routing choice into a
tracked artifact.

### One honest capability difference to report, not hide

A persona's lane does constrain what its turn can *do*: R14.3 ships a bounded
single-shot for both lanes, so no Buzz persona has tool use yet, and when a
nested agent loop lands it will be available only to agent-lane personas that
have the optional add-on installed. That is a property of the staffed model, not
of Buzz, and `golem buzz status` is the place to say so. **It must not change
the roster, the handles, or the provisioning.** See [[Buzz Integration]]'s
"Lane-transparent dispatch" section.

## The shape: generate, don't mutate

Buzz Desktop persists its managed agents to a JSON file reported at
`~/.local/share/xyz.block.buzz.app/agents/managed-agents.json`. **Do not write
to it.** Its schema is undocumented (§19 item 11 — sourced from a bug report,
not a spec), it is private Desktop state that may be rewritten under us, and
`block/buzz#4869` is open precisely because direct mutation is the wrong path.
If that control API lands, switching to it is a later task.

Instead Golem generates its own artifacts and supervises its own processes:

| Artifact | Where | Holds |
|---|---|---|
| Identity manifest | `.golem/buzz/agents.json` | persona id → pubkey, relay URL, respond-to mode, channel. **Pubkeys only — never a secret key.** Committed, so the roster is reviewable in a PR. |
| Launch spec | `.golem/buzz/agents.json`, same record | the `buzz-acp` env/flags for that persona (see below) |
| Harness definition | `<app-data>/custom_harnesses/golem.json` | the tier-3 BYOH JSON from R14.3, installed on demand |
| Secret keys | Golem's credential store (`src/credentials/`) | `BUZZ_PRIVATE_KEY` per persona, never in the repo, never in a `.env` file |

**Flagged trade-off:** the obvious alternative is a `.golem/buzz/<id>.env` file
per persona that the user sources. Rejected — it puts a Nostr secret key in a
plaintext file inside a git repo, one `.gitignore` mistake away from
publication. `golem buzz up` injects from the credential store at spawn time
instead (argument-array spawn, per `CLAUDE.md`). Say so in the PR if you take
the other path anyway.

## One `buzz-acp` process per persona — not one with `--agents N`

Confirmed in §19 item 9: **all N subprocesses behind a single `buzz-acp`
authenticate as the same Nostr identity** — "users see one bot regardless of
how many agents are running." `--agents` is a throughput dial, not a roster.
Distinct `@mention` handles therefore require distinct `buzz-acp` processes.
Per persona:

```
BUZZ_PRIVATE_KEY=<from Golem's credential store>
BUZZ_RELAY_URL=<project's relay>
BUZZ_ACP_AGENT_COMMAND=golem
BUZZ_ACP_AGENT_ARGS=acp,--persona,<id>      # splits on commas
BUZZ_ACP_RESPOND_TO=owner-only              # the most restrictive default
```

`owner-only` is already `buzz-acp`'s default and is the right floor — note its
sharp edge: an agent with no resolved `agent_owner_pubkey` under `owner-only`
responds to **nothing** until the owner resolves, which reads as a hang. Say so
in `golem buzz status`.

## The user-owned step, stated plainly

Registering a minted pubkey as a relay member is:

```bash
BUZZ_RELAY_PRIVATE_KEY=<relay signing key> buzz-admin add-member --pubkey <hex>
```

It needs **the relay's own signing key**, which makes it a credentialed
operator act. Golem mints the keypair and **prints this line**; Golem must not
run it. Same for installing `custom_harnesses/golem.json` into Buzz Desktop's
app-data directory — offer it behind an explicit `golem buzz install-harness`,
never as a side effect of `golem init`.

`buzz-admin`, `buzz-acp` and `buzz` (buzz-cli) are Rust binaries from
`block/buzz`. Golem cannot ship them and must not try to build them; detect
them on PATH and say what is missing.

### Claude Code is NOT a prerequisite — confirmed, and it cuts both ways

Checked 2026-09-20 (`verification-notes.md` §21 item 9), because the nested
agent-lane path would obviously need *something* Claude-shaped:

- **No separate Claude Code install.** `@agentclientprotocol/claude-agent-acp`
  depends on `@anthropic-ai/claude-agent-sdk`, which ships the native `claude`
  binary as a **platform-specific optional dependency**; `claudeCliPath()`
  resolves it through the SDK's own module graph and **never consults `PATH`**.
  One npm install brings the whole tree.
- **No `claude login` either.** `authenticate` with `methodId: "gateway"` points
  the nested session at Golem's own proxy and sets `ANTHROPIC_AUTH_TOKEN` to a
  literal `"acp-proxy"` whose in-source comment is *"Bypass local Claude login
  checks"*. The proxy holds the real credential.
- **But it IS a heavyweight native dependency**, which `CLAUDE.md` forbids in
  the default install. So it is an **optional add-on**, installed on demand,
  never a dependency of the default `golem-run` tarball — and it is needed only
  for the nested agent-lane executor, which is a later task. **Nothing in R14.2
  or R14.3 requires it.**

`golem buzz status` should therefore report it the way it reports the Rust
binaries: present or absent, with what it unlocks, and no attempt to install it
as a side effect.

**There are no prebuilt CLI binaries** — §20 item 6 checked the release API
directly, and all twelve assets of the latest release (`desktop-v0.5.23`,
2026-09-05) are Buzz **Desktop** installers. No Homebrew tap, no npm
distribution. The documented install is `cargo build --release -p <crate>`.

Two things soften that, and `golem buzz status` should say both rather than
just reporting a missing binary:

- **`buzz-admin` does not need a Rust toolchain.** It ships inside the relay
  container image:
  `docker run --rm --entrypoint /usr/local/bin/buzz-admin ghcr.io/block/buzz:main generate-key`.
  Since minting is the step Golem drives, prefer detecting Docker + that image
  as an equally valid path to a keypair, and print whichever line matches what
  the user actually has.
- **The relay itself can be hosted.** `just setup && just build` then
  `just relay` is the local path; a one-click Railway template and Block-hosted
  communities at `<name>.communities.buzz.xyz` (via `app.builderlab.xyz`, 3 per
  account) are the others. **Unconfirmed and worth stating as such:** whether a
  hosted community lets its owner register an agent pubkey without the relay's
  signing key — the in-app invite UI implied by `block/buzz#4209` looks like the
  path, but nobody has walked it. Do not write tooling that assumes it works.

## Settled: no per-persona `effort` field

The open question carried from [[Buzz Integration]] is answered (§19 item 10).
Buzz's `effort` dial (medium / high / xhigh) applies only to runtimes Buzz
launches with known flags. It cannot reach a tier-3 `golem` runtime, and there
is no documented CLI/REST/env path to set it anyway. **Do not add `effort` to
`inference.personas` for Buzz's sake.** If a per-persona reasoning dial is
wanted later it should be justified on Golem's own routing merits, as its own
task.

## Must not

- Do not write to `managed-agents.json` or any other Buzz Desktop private state.
- Do not put a secret key in the repo, a `.env` file, a log line, telemetry, or
  the KB.
- Do not change `.claude/agents/golem-<id>.md` generation — this is an
  additional export alongside it.
- **Do not filter the roster by lane.** `resolveDesiredAgents()`'s
  `lane.kind !== "agent"` skip is correct for `.claude/agents/` and wrong here;
  copying it would silently drop every worker-lane persona from Buzz.
- **Do not put the lane, the model, or the target id in the committed

- Do not default any persona to `anyone`.
- Do not implement dispatch behaviour — identities and wiring only (R14.4).
- Do not build on Buzz's persona packs (`--persona-pack` / `--persona` /
  `--workdir`): PR #7359, open and unmerged — re-checked 2026-09-19 (§20 item
  7), still open, direction unchanged.
