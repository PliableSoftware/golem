## What this is

Extend Golem's existing persona-sync (the mechanism that already generates
`.claude/agents/golem-<id>.md` per staffed persona, per
`.claude/rules/golem-prefer-persona-agents.md`) to also provision a **Buzz**
agent identity for each staffed persona, so `golem-coder`, `golem-planner`,
`golem-reviewer`, `golem-scribe` (or whatever the current roster is) appear as
addressable agents in that project's Buzz workspace.

Full design: [[Buzz Integration]] (`docs/wiki/concepts/Buzz Integration.md`).
Read it before starting — this brief does not restate the mapping table,
identity/scoping rules, or the auto-sync decision, all of which are settled
there (USER, 2026-09-19).

## Must

- One Buzz agent identity (own keypair) per staffed persona, scoped to the
  **project**, not shared globally across Golem projects.
- Golem CLI is the provisioner — not a manual Buzz-UI setup step for the user.
- Buzz agent's harness = `claude`, model = `inference.personas.<id>.model`,
  agent instructions = the same role prompt currently written into
  `.claude/agents/golem-<id>.md`.
- Auto-sync: a persona roster/model/prompt change re-runs the export, same
  trigger point as the existing `.claude/agents/golem-<id>.md` regeneration.
- Respond-to starts at the most restrictive setting Buzz offers (`Only me` /
  project owner as trust root) — do not default personas to a public or
  team-wide mention surface.

## Must not

- Do not invent a config format speculatively. If Buzz's provisioning surface
  turns out to be UI-only with no scriptable path, that is a valid finding —
  report it and stop rather than shipping a script against guessed shapes.
- Do not change `.claude/agents/golem-<id>.md` generation itself; this is an
  additional export alongside it, not a replacement.
- Do not touch the reverse direction (Golem itself addressable in Buzz) —
  that's [[R14.3]].
