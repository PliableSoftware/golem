## What this is

The orchestration half of [[Buzz Integration]], on top of R14.3 (`golem acp`)
and R14.2 (identities). A human or another agent `@mention`s **Golem** in a
project channel; Golem's orchestrator — its own `buzz-acp` process with its own
Nostr identity — resolves the request the way it does today (task doc lookup,
clarification) and dispatches by posting `@mention` messages to the persona
agents from R14.2, in the same thread, instead of calling the `Agent` tool.

The transport-vs-content split is the settled design decision (USER,
2026-09-19): **the dispatch prompt content does not change, only the transport
and the completion signal.** Do not re-litigate it; if it proves unworkable,
that is a `verification-notes.md` finding, not a silent redesign.

## The one thing the design got wrong: turns are not resumable in memory

[[Buzz Integration]] says Golem "watches the thread". It cannot. Confirmed in
`verification-notes.md` §19 item 7:

- `buzz-acp` holds **at most one prompt in flight per channel**. An
  orchestrator that blocks waiting for a persona reply deadlocks the channel
  that the reply has to arrive through.
- `BUZZ_ACP_IDLE_TIMEOUT` defaults to **620 seconds** and cancels a quiet turn.
- Queued events are **drained into a single batched `session/prompt`**, so two
  persona replies can arrive as one prompt, in one turn.
- `!rotate` invalidates the ACP session, and `buzz-acp` respawns the agent on
  crash. Process memory is not a place state survives.

So the orchestrator is a **state machine across turns, not a loop within one**:
receive a prompt → read durable state for this thread → post zero or more
messages → **end the turn** → be woken later by a reply that mentions it. The
gate is written to prove exactly this, because an implementation that works in
one long turn will pass a naive test and fail in a real channel.

## Files, in the order to touch them

1. **`src/buzz/cli-client.ts`** — a typed wrapper over the `buzz` CLI, which is
   how an agent posts (§19 item 8; there is no ACP method for it). JSON in,
   JSON out; exit codes **0 ok · 1 user error · 2 network · 3 auth · 4 other ·
   5 write conflict** — map each, and treat 5 as retryable and 3 as fatal.
   `buzz-acp` pre-injects `BUZZ_RELAY_URL`, `BUZZ_PRIVATE_KEY` and
   `BUZZ_AUTH_TAG` into the subprocess environment, so no credential handling
   belongs here. Argument-array spawn, cross-platform, per `CLAUDE.md`.
   The dispatch call is:

   ```
   buzz messages send --channel <uuid> --reply-to <thread-root-id> \
     --mention <persona-pubkey> --content -
   ```

   with the dispatch prompt on stdin (`--content -`). **Use `--mention` rather
   than an inline `@Name`** — §19 item 6 records that Buzz matches mentions on
   the `p` tag, and an inline handle changes the message body.
2. **`src/buzz/thread-state.ts`** — durable per-thread state under
   `.golem/state/buzz/<thread-root-id>.json` (gitignored): which task, which
   personas dispatched and when, which replied, what the sequence is, what has
   already been posted. Must be idempotent against replay — §19 item 7 records
   that `buzz-acp` **replays all unprocessed @mentions on startup**, so the
   same dispatch event can arrive twice and must not produce two dispatches.
   Key the dedupe on the Nostr event id.
3. **`src/buzz/orchestrator.ts`** — the state machine. Given an inbound prompt
   (possibly several batched events) plus thread state, decide: acknowledge,
   ask for clarification, dispatch the next persona, or summarise and finish.
   Reuses the existing dispatch-prompt content builder — the persona prompt
   from `resolvePersonaPrompt()` in `src/inference/personas.ts` plus the task
   brief — unchanged, so a persona reads the same brief whichever transport
   carried it.
4. **`src/buzz/acp-turn.ts`** (from R14.3) — route a turn to the orchestrator
   when the process was launched as the orchestrator identity, and to the plain
   persona path otherwise. One branch, at the top; keep the rest shared.
5. **`tests/unit/buzz/`** — drive the orchestrator across separate turns with a
   scripted ACP client and a faked `buzz` CLI. Assert: no dispatch is repeated
   on a replayed event; two batched replies in one prompt advance the sequence
   once; a turn that dispatches also ends.

## Sequencing and scope

- Sequence planner → coder → reviewer → scribe the way the inline flows do
  today, but one dispatch per turn — the thread is the queue.
- Post an **ack** on first mention before any long work, so the channel shows
  the request was taken up.
- Ambiguity mirrors today's clarification behaviour, posted as a channel reply
  rather than an `AskUserQuestion` call — and then the turn ends, like any
  other.
- Prefer the **`thread` session-scope policy** over the default `channel` one
  so concurrent tasks do not interleave in a single ACP session. The flag that
  selects it was not captured in the README read (§19 item 9, unconfirmed) —
  find it in `crates/buzz-acp` and record it before relying on it.
- Consider whether the orchestrator should run with a `--heartbeat-interval`
  (§19 item 7) to sweep threads that stalled. It is best-effort — dropped when
  busy, never queued — so it is a safety net, not a mechanism. Decide, and say
  which.

## Must not

- Do not hold a turn open waiting for a persona reply.
- Do not keep sequence state in process memory between turns.
- Do not remove or bypass the synchronous `Agent`-tool dispatch path for
  non-Buzz sessions — this is an additional entry point.
- Do not proceed silently when the request cannot be resolved.
- Do not let the orchestrator dispatch to a persona outside the project's
  provisioned roster from R14.2.
