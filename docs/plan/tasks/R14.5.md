## What this is

Confirmed-viable (`verification-notes.md` §21) but deliberately unscoped
placeholder for tier C of Buzz's persona lane-transparency design (see
[[Buzz Integration]], "tiers A/B/C"): running an agent-lane persona in Buzz
by nesting `@agentclientprotocol/claude-agent-acp` as a child ACP agent
inside `golem acp`, so a persona whose model names a real subagent-capable
model gets an actual tool-use loop in Buzz, not just the one-shot dispatch
tier B already covers.

This task exists only so R14.3's "It gets its own task doc" and the wiki's
"Tier C ... wants its own task doc" have somewhere real to point — it is not
yet a startable brief. Do not treat its presence as permission to scope or
implement tier C.

## Why it is `owner: user` and has no gate yet

Every tool call in the nested session round-trips through
`session/request_permission`. The upstream reference client auto-allows
everything, which in this context means: an unattended process, woken by a
chat message from anyone with mention access, gets unsupervised write access
to a real repository and can run commands. That is a permission-model
decision with real blast radius, not an implementation detail a coding pass
can default its way past. It was asked directly (2026-09-20) and the answer
was to defer it, not to pick a default — so this task cannot honestly carry
a `size`, `gate`, or `touches` list yet. The `L` size above is a placeholder,
not an estimate.

## What unblocks it

A decision — from the user, in a future conversation — on one of:

1. **Human approval in-channel**: a tool call that would write or execute
   posts a request back to the Buzz channel and waits for the project owner
   to approve before proceeding.
2. **Scoped auto-allow**: a defined safe subset (e.g. read-only plus edits
   within the repo, never shell or network) is auto-approved; anything
   outside it requires approval.
3. **Full auto-allow**: trust the persona the way an already-vetted CI job is
   trusted. Matches the reference implementation's own default. Accepts the
   risk `verification-notes.md` §21 flagged rather than mitigating it.

Once one is chosen, re-scope this task: name the actual gate, the files it
touches (likely a permission-bridging module wired into `acp-agent.ts` from
R14.3, translating `session/request_permission` calls from the nested
session into whatever the chosen posture requires), and its size for real.

## Must not

- Do not implement any part of tier C, including a "temporary" default
  permission posture, before the decision above is made.
- Do not let R14.3 or R14.2 grow tier-C behavior to compensate for this being
  unscoped — both are already correctly bounded to tiers A/B.
