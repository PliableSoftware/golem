## Problem

`trimOutput` (line 166) and `fileBackend.get` (line 448) both use `.trim()`, which strips ALL leading and trailing whitespace. The encoding layer only adds a trailing newline (`${secret}\n` in fileBackend.set, or the CLI helper's single trailing newline), so the correct inverse operation is to strip one trailing `\r?\n`, not all whitespace.

If an API key or password contains intentional leading/trailing whitespace (rare but possible for passwords, some legacy tokens), the credential would be silently corrupted on round-trip.

## Fix

Replace `.trim()` with `.replace(/\r?\n$/, "")` (strip exactly one trailing newline) in:
- `trimOutput` (line 166): `s.replace(/\r?\n$/, "").trim()` → `s.replace(/\r?\n$/, "")`
- `fileBackend.get` (line 448): `.trim()` → `.replace(/\r?\n$/, "")`

Keep the `=== ""` empty-check (a secret of only newlines should read as null/absent).

## Out of scope

- The DPAPI / macOS / Linux backends (they have their own encoding boundaries, verified correct)
- Changing the store's empty-credential refusal

## Outcome (2026-10, fix/credential-trim)

**Backends are byte-exact on read.** One trailing `\r?\n` is stripped (`stripOneNewline`, the
inverse of the `${secret}\n` file encoding and of the CLI helper terminator); `trimOutput` (full
trim) remains only for helper diagnostics and non-secret blobs. A newline-only value reads as absent.
libsecret and the DPAPI batch decode strip nothing; DPAPI encrypt no longer `.Trim()`s the plaintext
(pinned by a static test). Line numbers above were stale; every `trim()` on a secret path was changed.

**Gateway key ingestion** (piped stdin, prompt, `add --login`; `src/credentials/validate.ts`) trims ALL
leading/trailing whitespace (spaces, tabs, NBSP, Unicode spaces, BOM, any number of newlines) because an
API key never has any (this makes cmd's `echo KEY |` and `key\n\n` harmless; interior spaces stay),
then refuses, without echoing the key, any control character, U+FEFF, or code point above U+00FF
(undici rejects those per request, even with `--no-probe`). Every refusal is an `InitError`, exit 2,
ending "Nothing stored."; newline-only stdin says "no key was provided on stdin".

**Read-side compatibility rule** (`src/credentials/store.ts`): for gateway-kind accounts the store trims
leading/trailing whitespace on read. Builds before R8.29 stored a prompted key untrimmed and trimmed on
every read, so such keys may already exist; without this an upgrade would start sending them with the
whitespace. A gateway API key never legitimately has edge whitespace. `portal-oauth` and `buzz:`
accounts stay byte-exact. The kind is guessed from the account NAME and only for this trim, so a
gateway someone names `buzz:x` merely stays byte-exact (see the follow-up on reserving those ids).

**Probe:** an undici malformed-header `InvalidArgumentError` is reported as a `rejected` (malformed key)
verdict, not `inconclusive`, so it blocks the store.

**Known gap, no behaviour change:** a stored secret ending in `\r` comes back without it from the file
and macOS backends but with it from single-key DPAPI. A CR is refused at ingestion, so only a
hand-edited store is affected.

**Not covered:** `--value-file` in `src/cli/config.ts` feeds config values, not credentials, and still
trims. Live PowerShell is unverified off Windows (a `pwsh.exe` stand-in covers the single and batch
paths with CRLF output).

### Reviewed and deliberately NOT pursued here

An earlier iteration of this branch added a read-side "malformed stored key" subsystem (a throwing
`resolve`, per-account faults, a `golem status` credential line, a proxy-start warning, Buzz and portal
handling). Review kept finding new defects in it (upgrade regressions, `provisionBuzz` orphaning,
`golem status` polling the keychain, name-based kind guessing, non-hermetic tests), so it was removed.
Follow-up: `credential-malformed-visibility`.
