# R13.8: start and continue a conversation from the device

Closes R13.8 (depends on R13.3, R13.6, both done). A device can now pick a
known project, start a new conversation in it, resume an existing one — live,
or after its runner process has exited — and page back through what was said.
Design page: [[Device Conversations]].

## What shipped

- **`known-projects.ts`** — a user-scoped registry (`~/.golem/state/known-projects.json`)
  a device can ask "what projects does Golem know about", separate from any
  one project's own `.golem/` directory. Every read re-checks the root live
  (`checkReachability`) rather than trusting the stored record, and names
  exactly what is missing — `not_wired` names the specific missing piece
  (`.golem/settings.json` or `.claude/`), `unreachable` names the path.
- **`device-sessions.ts`** — `GET /api/projects`, `POST /api/conversations`
  (origination gated by `security.origination_roots`, checked after
  `resolveWorktreeRoot` so a symlink cannot widen it), `GET /api/conversations/:id`
  (resume — live / restarted via `--resume <runnerSessionId>` / cross-process
  409 / never-completed 409), and `GET /api/conversations/:id/messages`
  (paged scrollback, `before`/`limit`, capped at 200).
- Identity: a device-started conversation's host-registry id is set to
  `conversationIdFor({ messages: [...] })` — the same function
  [[Conversation Store]] and `session-tree.ts` already share — so the project
  list, resume path, and scrollback all agree on what they are talking about
  by construction, not by a second join table.
- Test coverage: a new unit suite for `known-projects.ts` (10 tests) and a
  new integration suite for `device-sessions.ts` (10 tests) driving a fake
  runner script instead of the real `claude` CLI, plus two `runnerArgs` unit
  tests for the `--resume` flag added to `HostedSessionOptions` in a prior
  session on this branch.

## Two real bugs the task's own tests found

Not bugs in a spec — bugs a *correct-looking* implementation had, caught only
because the scrollback test was written to assert on actual content rather
than "the call succeeded":

1. **`deliver()` silently dropped every message after the first.** The first
   user turn is appended to the conversation store by `startConversation`
   before the runner process even starts. Every *subsequent* device message
   went straight to `hosted.send(text)` and never touched the store — so
   scrollback showed the opening message and every assistant reply, but
   never anything the device said back after that. A test asserting turn
   *count* alone (`length === 4`) would have passed with the wrong 4 turns;
   asserting on `[role, content]` pairs in order caught it immediately.
2. **Both `history()` and the scrollback route read from the wrong store.**
   `options.projectDir` is the handler's own project — but item 2 means a
   conversation can legitimately live in a *different*, allowlisted root.
   Both read sites used the handler's fixed store rather than the
   conversation's own root, so a cross-root conversation would silently show
   empty scrollback instead of failing loudly. Fixed by scoping both to the
   conversation's actual root (`entry.projectDir` while live; `live.get(id)?.projectDir
   ?? options.projectDir` in the route). The remaining gap — a cross-root
   conversation surviving a `session host serve` **restart** — is harder to
   fix honestly (the new process's own-root registry never saw it), so it is
   documented as a stated limitation with an explicit 404 rather than left
   silent or patched over under time pressure.

## Fire-and-forget writes, and the one polling helper that covers all of them

Both `wireHostedSession`'s `"result"` handler and the `"exit"` handlers in
`startConversation`/`resumeConversation` publish a `SessionBus` event
(`turn_end`, `ended`) **before** the corresponding disk write
(`store.appendTurn`, `updateHostSession`) resolves — deliberately, to keep the
write off the event's hot path. That means a test (or a real reader) that
observes the bus event is not yet guaranteed the write has landed. Four
distinct test failures traced back to exactly this shape; all four converged
on one `waitFor(fn, timeoutMs)` polling helper rather than four bespoke
retries, which is now the pattern for any future test in this file.

## What is explicitly NOT done

- Forking a conversation at an earlier turn — dropped by ADR-0007 Revision 1,
  not touched here.
- Cross-machine sessions, non-Claude runners, editing files from the device,
  rewinding or mutating a live harness session — all out of scope per the
  task brief.
- The `conversationIdFor` vs. `session-tree.ts`'s independently-observed hash
  equality — stated as related-but-unproven in both the module docblock and
  the wiki page, not verified empirically this task.
- End-to-end argv assertion that `HostedSession.start()` actually includes
  `--resume` when spawning the real `claude` CLI — only `runnerArgs()` in
  isolation is asserted; the integration test exercises the full
  `resumeConversation` path via `runnerArgsOverride`, not real argv.
